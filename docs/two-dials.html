The two dials

Every piece of work in SDD runs with two settings. They are independent: one describes the change, the other describes the product. Together they decide how much process you get. Small work stays light, and important work gets the proof it needs.

Size decides the paperwork. Assurance decides the proof.

Picking the size: ask from the top

  1. Migration, public API, security, irreversible?full
  2. Several areas, or a new component or interface?standard
  3. One area, up to ~5 requirements, nothing new?mini
  4. Typo, one-line fix, config tweak?inline

Picking the assurance: ask from the top

  1. Money, security, safety, regulated, irreversible?critical
  2. External users, or business data that persists?production
  3. Used by you or your team, with real data?internal
  4. Demo or experiment; may be thrown away?prototype
Both ladders: start at the top, and the first “yes” wins. Unsure between two? Take the higher one.

Always true, at every setting

  • Every requirement has an ID, e.g. REQ-CHK-007.
  • Tests are written before the code they test, and named after their scenario.
  • When a change is done, the living spec is updated to match.
  • All state lives in the specs/ folder, so any session in Claude Code or Codex can pick up where the last one stopped.
  • If coding shows the spec is wrong, work stops and the spec change comes to you (sdd amend).

When a prototype grows up

The Known gaps list is not waste: it is the to-do list for hardening.

prototype→production

sdd harden checkout --to production

The reviewer turns each known gap into failure-case scenarios and tests, delivered as one normal standard change. Prototypes cost nothing extra up front, and nothing is forgotten when they become real.
