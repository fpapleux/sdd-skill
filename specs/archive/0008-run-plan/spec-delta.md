## Requirements

### REQ-ORC-009 Run-plan prints the steps of a run
When the operator runs `sdd.py run-plan [<form>]` for the active change, or the one `--change` names, at planned or implementing, sdd.py shall print the test steps of the run that `implement <form>` makes and exit 0, running no command and changing no file: the form is `T<n>` (that task), `T<a>-T<b>` (the tasks from T<a> to T<b> in plan order), `next` (the first unticked task; the default) or `all` (every task of the plan); `Test command:` and `Test one:` are each read from the first list line (`-` or `*`) of the design (design.md of a standard change, the Design notes of a mini one) that carries it, as REQ-EVD-004 reads `Test component:`, taken without surrounding backticks, and a mention elsewhere in the change does not count; the first line is `plan for <change-id> (<form>): <n> to do, <m> done`, where n and m count the unticked and the ticked tasks of the range; after it, or after the skipped line of REQ-ORC-010 when there is one, comes the baseline line, read from the change's baseline.txt (REQ-EVD-008): `- baseline: none (the design has no "Test report:" line)`, unnumbered, when the design has no `Test report:` line or an empty one and no baseline.txt, otherwise `1. baseline: <test command>` when the change has no baseline.txt and no ticked task, `- baseline: none (a task is ticked; runs sort without one)`, unnumbered, when it has no baseline.txt and a ticked task, or `- baseline: recorded <time>`, unnumbered, with the time of its first line, when it has one; then one line per task of the range, in plan order; for an unticked task, first `<k>. T<i>: <Test one> (no test line yet)` when the task has no test line (empty or a placeholder, as replay reads it, REQ-EVD-001), where `<Test one>` is the `Test one:` command as written, without backticks; otherwise `<k>. T<i>: no command (the test line has no "::")` when that command uses `{file}` or `{name}` and the test line has no `::`; otherwise `<k>. T<i>: <command>`, where the command is the `Test one:` command split into words as a shell splits them, then each `{test}`, `{file}` and `{name}` filled inside its word from the task's test line as replay fills them (REQ-EVD-001), the words joined by single spaces, a word being single-quoted when it is empty or holds a character other than an ASCII letter, an ASCII digit or one of `@%+=:,./_-`, with a single quote inside it written `'"'"'`; and `- T<i>: done`, unnumbered, for a ticked task, with the component checkpoints of REQ-ORC-010 placed among them; and last `<k>. full suite: <test command>`; the test command is the `Test command:` text as written, without backticks, and k numbers the numbered lines from 1; a range with no unticked task prints only the first line, the baseline line, its done lines and `nothing to run: no task to do in the range`.

### REQ-ORC-010 Run-plan places a component checkpoint after each group
When `sdd.py run-plan` prints a plan with an unticked task, sdd.py shall print a component checkpoint, `<k>. component <PREFIX>: <command>`, where the command is the design's `Test component:` command (REQ-EVD-004) with every `{prefix}` replaced by PREFIX, for each group of unticked tasks of the range that share a requirement prefix with no unticked task of another prefix between them, a task's prefix being the prefix of its first scenario reference; the checkpoint comes right before the next unticked task with another prefix, or after the range's last task; a ticked task, or a task with no scenario reference, is listed but neither joins nor ends a group; and when the design has no `Test component:` command, or an empty one, sdd.py shall print `component checkpoints skipped: the design has no "Test component:" line` right after the first line and no component step, the full suite staying the last step.

### REQ-ORC-011 Run-plan refuses what it cannot plan

### REQ-EVD-007 Run a test step and report its exceptions
When the operator runs `sdd.py test <step>` for the active change, or the one `--change` names, at planned, implementing or verifying, where the step is `T<n>` (the task's own test), `component <PREFIX>` (the capability's tests) or `full` (the full suite), sdd.py shall run the step's command as `run-plan` prints it (REQ-ORC-009, REQ-ORC-010), as its words with no shell, from the folder that holds specs/, and wait for it to end; once the command has started, sdd.py renames the previous last run's files, if any, from `specs/.sdd/runs/last-run.json` and `last-run.log` to `run-of-<its time>.json` and `.log`, the time written with `-` for `:` (`run-of-2026-11-16T09-00-00Z`) and `-2`, `-3`… added when that name is taken, which the folder's `.gitignore` (holding `run-of-*`, written when missing) keeps out of git; then it writes the run's record (the time, the change, the commit, the step, the command, its exit code, each test's outcome and the digest of REQ-EVD-009) to `last-run.json` and the command's full output to `last-run.log`, which git tracks, writing each occurrence of the project folder's absolute path as `.` in both files and in the report; a time is UTC to the second, as `2026-11-16T09:00:00Z`. sdd.py shall print the report: `test <step>: <command>`; then `result: <p> passed, <f> failed, <e> errors, <k> skipped (<n> tests) in <s>s`, s being the wall-clock seconds with one decimal; then, for each test that failed or errored, `failed: <name>` or `error: <name>`, followed by at most 5 lines, each indented by two spaces, taken from its failure or error element's `message` attribute and then its text, or `  (no message)` when both are empty; then the lines of REQ-EVD-005 for those names, sorted against the change's baseline as REQ-EVD-006 does when it has one (REQ-EVD-008), and otherwise with `warning: no baseline recorded; a test that passed before the change is sorted as outside` before the `sorted:` line; then `warning: the command exited <code> but the report shows no failure` when the command exits other than 0 and no test failed or errored; and last `log: specs/.sdd/runs/last-run.log`. Each test's outcome is read from the JUnit XML report at the path the design's `Test report:` list line names, read like `Test one:` (REQ-ORC-009), which sdd.py deletes before the run so a report left by an earlier run is never read; a test's name is its `classname`, a dot and its `name`, or its `name` alone when it has no `classname`. When the design has no `Test report:` line, or an empty one, or the run leaves no report there that can be read as JUnit XML, sdd.py shall print, in place of the result, test, sort and exit-code warning lines, `result: exit <code>, no test report: each test's outcome is unknown`, then the last 20 lines of the output, each indented by two spaces. When `last-run.json` can't be read as a run record, sdd.py shall rename it and its log to `run-of-unreadable-<now>.json` and `.log`, print `warning: last-run.json could not be read; kept as run-of-unreadable-<now>.json` and run the step. When the command can't be started, sdd.py shall print an error that names it and exit 1, recording no run and renaming nothing. sdd.py exits 1 when a regression is sorted, when the exit-code warning is printed, or, with no test report, when the command exits other than 0; otherwise 0.

### REQ-EVD-008 Record the tests that pass before the change, once
When the operator runs `sdd.py test baseline` for a change at planned or implementing that has no ticked task, no baseline.txt and a `Test report:` line, sdd.py shall run the full suite as `test full` does (REQ-EVD-007) and print its report with the first line `test baseline: <test command>` and no baseline warning, then write the change's baseline to `baseline.txt` in the change's folder (its first line `# baseline <time> <commit>`, the commit being `none` outside a git repository or before its first commit, then the names of the tests that passed, one per line), which git tracks and archive moves with the change, and print `baseline: <p> tests passed, recorded <time>`; every later `test` run of the change sorts against that baseline, which is never rerun or changed; when the full suite's run is reused (REQ-EVD-009), the reused run counts as the baseline's run and baseline.txt carries its time. When its run leaves no test report, sdd.py shall print the report of REQ-EVD-007, then an error that a baseline needs a test report, write no baseline.txt and exit 1. Its own refusals (a baseline.txt already there, a ticked task, a status other than planned or implementing, no `Test report:` line) come after the step in REQ-EVD-011's order, in that order, before anything is run.

### REQ-EVD-010 Write a task's red and green lines from its run

## Known gaps
<!-- Behavior deliberately not handled, one line each. Required at prototype
(write "- None" if there are none). -->
- A capability declared with two prefixes gets one component checkpoint per prefix, each running part of its tests, not one checkpoint for the capability (0005 Q4).
- A task whose scenario references carry two prefixes is grouped by its first reference only; its other prefix gets no checkpoint from it.
- run-plan prints the `Test component:` command as written: a command without `{prefix}` or with a quote that doesn't close is reported by check at the plan stage (REQ-EVD-004), not by run-plan.
- run-plan runs no step, ticks no task and records no evidence; `sdd.py test` runs the steps (REQ-EVD-007), and ticking a task stays the agent's.
- A run that spans several changes, and components other than capabilities (such as architectural layers), are not planned.
- The plan lists the test steps only: `advance implementing` at planned and the check after each task stay in implement.md (round 1 Q1); the sorts are in the `test` report (REQ-EVD-007).
- check at the plan stage and `advance designed` read `Test command:` as its first mention anywhere in the change, and replay and mutate read `Test one:` as its first list line anywhere in the change, not from the design's list line that run-plan reads, so a prose mention or a list line outside the design can stand in for the design's line and the command replay runs can differ from the one run-plan prints; this defect is outside this change, and the operator decides on a separate defect change.
- That `implement` follows the printed plan is method work under project rule 1, verified by review and a dogfood run.
- A test run that never ends is not stopped: sdd.py waits for the command to end.
- A step reuses only the last run (Q4), so steps that alternate (a task, its component, the full suite) rarely reuse one; earlier runs stay as run-of files that git ignores, on the machine that ran them. A change planned before this rule has no baseline.txt, so its runs sort as REQ-EVD-005 did, with the warning.
- A baseline is refused once a task is ticked, but a code edit made before the first tick, outside a task, is not detected: the baseline then holds the edited code's results.
- A red line that holds only after an earlier task's code (`(after T<n>)`) and a `red: pre-existing` line are still written by hand; `test --red` writes neither.
- A runner that can't write JUnit XML gets the exit code and the last 20 lines only: no per-test outcome, no sorting, no red or green line. A project's own adapter that writes the report (as this repository's unittest one, in the design) is the way round it.
- Reuse compares file content, not what the tests read: a change to a file git ignores, an environment variable or a service the tests call doesn't stop a reuse; --rerun runs the step anyway.
- That implement and verify run their test steps through `sdd.py test`, and read its report instead of the output, is method work under project rule 1, verified by review and a dogfood run.
- Only the project folder's absolute path is written as `.`: other local paths in a runner's output (the home folder, a virtual environment, a temporary folder) are kept as they are in the committed last-run.log, and a project rule against local paths in committed files is checked by the operator.
- A red or green line typed by hand in the form sdd.py writes, with "(sdd test <time>)", is not told apart from one sdd.py wrote: the mark isn't checked against a recorded run.
- Two `sdd.py test` runs at the same moment can overwrite each other's report and last run (concurrency is not required at production).
- Duplicate test names in one report are counted as the report lists them, and a name that both passed and failed counts as failed.
- A runner's output is kept whole, with no size cap, and a large last-run.log is committed.
- Files a runner writes that git doesn't ignore (caches, coverage data) change the digest, so no run is reused after them.
- A test line holding `{name}` or `{file}`, or several `::`, is filled as replay fills it (REQ-EVD-001), for the defect change on the loose readers.
- No platform is named: Windows paths in commands and a missing `python3` are not handled.
- A test name with surrounding spaces or a newline doesn't survive baseline.txt, so it isn't matched to the baseline.
- A range with nothing left to run still prints "component checkpoints skipped" when the design has no Test component line (verification F2).
- No test catches the reused suffix on a result line with no report, a submodule in the digest, the skip of a tracked file deleted in the working tree, or write_evidence keeping CRLF line endings and ending its block at a heading (verification F4).
- A file the runner creates gets the umask default mode; only an existing file's mode is kept (verification F3).
